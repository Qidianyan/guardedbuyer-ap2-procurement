# Known failure cases and limitations

We list what does **not** work or is not proven yet. Each entry: what happens, why, and what we do about it.

| # | Failure / limitation | Evidence | Mitigation now | Next step |
|---|---|---|---|---|
| 1 | **The real LLM still picks the poisoned quote.** In the red-team run, deepseek-v4.1-flash recognised the injected "SYSTEM NOTICE" but still submitted the cheaper GadgetGuru quote. | `scenarios/run_all.py --llm`, scenario 4b (single run); in the 12-case LLM sample (`docs/metrics.md`), the model bought from the poisoned merchant in 3/12 cases with no guardrails and 2/12 with full guardrails | Quarantine blocks purchases from merchants whose listing carries injection indicators; the model then re-ordered from a clean merchant. | Measure over more runs; give the model the exclusion list up front. |
| 2 | **The injection detector is regex-based and evadable.** Polite, business-style injections are not flagged. | `docs/metrics.md`: injection templates with `detector_should_flag = false` | Detection is only a signal. Scope guard, policy, approvals and the mandate still apply. | A classifier-based detector; per-merchant reputation. |
| 3 | **In-scope purchases from an evasive attacker can succeed.** If an undetected injection convinces the agent to buy the *requested* item from the attacker's own store (in scope, in policy), no layer objects. | Offline: `injection/official_supplier` 0/5 blocked with full guardrails (the only miss in the set). Real LLM sample: the 2 payments that got through with full guardrails were in-scope purchases from an undetected poisoned merchant that had the cheapest quote | Purchases above $500 still need a human approver; everything is in the audit log. | Merchant allow-list / vendor onboarding; require approval for first-time merchants. |
| 4 | **The scope guard depends on a deterministic parser.** If the employee's text can't be parsed (unknown item, odd phrasing), there is no scope limit and only policy, approvals and the mandate apply. | `procure/tool_agent.py::_derive_scope` | Logged as `scope=None` in `agent_task`. | Have the employee confirm the parsed scope in the UI before the agent runs. |
| 5 | **Buyers can't create disputes via API.** PayPal Disputes v1 has no buyer-side create endpoint. | PayPal API reference (Disputes v1 endpoint list) | In the sandbox the agent prepares the claim (`dispute_prepared_for_buyer`) and a person files it; the emulation simulates the filing. | Sandbox walkthrough with the Resolution Center; track status by ID. |
| 6 | **The PayPal sandbox has not been exercised.** All PayPal behaviour in the demo is the offline emulation built from PayPal's OpenAPI specs. | README "Status" | Emulation follows the official schemas; the toolkit's own handlers run against it. | Run with sandbox credentials; compare responses field by field. |
| 7 | **Overcharged invoices produce no refund claim.** If the receipt shows a higher unit price but PayPal charged the mandated amount, nothing is claimed; the case is flagged for review. | `procure/agent.py::receive` (`receipt_discrepancy_flagged`) | Intended: the money PayPal moved matches the mandate. | Compare against the merchant's invoice/charges if they bill outside PayPal. |
| 8 | **The mandate is self-issued.** Local Ed25519 key, not an AP2 credential from a wallet/issuer; spend limits are our own extension. | `procure/mandate.py` docstring | Clearly labelled in the README and UI. | Integrate an AP2-compatible credential provider. |
| 9 | **The LLM gateway gets rate-limited.** The shared endpoint returns HTTP 429 under load. | Logs during development | Exponential backoff; the agent loop falls back to the offline planner and records `llm_fallback`. | Use a dedicated key for the hosted demo. |
| 10 | **Human approvers are assumed correct.** The evaluation assumes approvers only approve the legitimate purchase. | `metrics/run_metrics.py` docstring | Approval reasons and the amounts are shown to approvers in the UI. | Show the agent's evidence (quotes, flags) on the approval screen. |
